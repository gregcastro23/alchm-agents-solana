Feed preview construction now defers local persistence to its authenticated publisher. Evaluating a preview performs neither local comment writes nor WTEN delivery.

Adaptations also carry `instructionReviewRequired: true`. Exact ingredient references are rewritten, but abbreviated references, cooking methods, and timings cannot be reliably reconciled by string replacement. These remain recipe proposals requiring review before cooking.

## What the data and integration actually establish

The checked-in snapshot contains **1,000 unique recipes** with nonempty ingredient and instruction lists. Its metadata reports **1,099 total recipes**, so it is a partial snapshot of the source catalog. **298 of the 1,000 recipes lack nutrition data.** Snapshot presence does not establish culinary quality, ingredient safety, or nutritional accuracy.

Menus now preserve catalog base IDs. Their adaptations, ingredient text, and nutrition totals are still generated by a model; those fields have not been independently verified. The substitution engine uses authored correspondence rules and historical agent profiles. These are creative persona behavior, not demonstrated nutritional effects.

Read-only inspection of the sibling WTEN checkout established that `/api/feed` accepts `recipe_generation` with `source: recipe_alteration`. Its feed insertion and recipe-comment mirror are separate operations: mirror errors are logged without failing the feed acknowledgement. The acknowledgement contains no comment-persistence result. See `src/services/feedDatabaseService.ts` and `src/app/api/feed/route.ts` in that checkout. No production publication was used for these checks.

The upstream community-tips endpoint returns a limited set of top-rated tips, not complete comment history. It can also return an empty list after an internal database failure; the local route cannot detect a failure hidden by the upstream contract.

## Next upgrades

1. **Version and refresh the snapshot explicitly.** Record source revision, export time, pagination completion, checksum, and schema validation during a controlled import. Complete the remaining catalog pages instead of claiming full coverage from `limit=1000`.
2. **Make recipe publication durable.** Give alterations caller-supplied idempotency keys and a durable pending/confirmed/uncertain ledger, as weekly menu publication now has. Current alteration deduplication binds generated content within a time window; it is not a complete replay contract for a caller retry.
3. **Confirm both downstream writes.** WTEN should return separate durable feed and comment outcomes, or provide a reconciliation endpoint. An atomic transaction/outbox would remove the present acknowledgement ambiguity.
4. **Separate recipe facts from generated adaptations.** Preserve source provenance, attach explicit substitutions, and calculate nutrition and dietary labels from the resulting ingredient quantities before presenting them as verified facts.
5. **Paginate recipe history.** Add cursor pagination and stable source identifiers. Keep partial-source status visible to clients and avoid claiming complete history from either bounded endpoint.

## Validation scope

Checks use an isolated source snapshot with mocked database, identity, model, and outbound-delivery boundaries. Catalog loading is exercised from a different process working directory. Negative cases cover denied publishers, unknown recipes, provider-invalid menus, unavailable comment sources, and unconfirmed remote comment persistence.

The Phase 2 backend suite previously passed 286 tests plus a separately enabled stdio round trip; its targeted frontend suites passed 81 tests. The recipe follow-up passed 141 tests across its combined focused suites and adjacent publication/feed regressions. Scoped strict TypeScript checks cover menu generation, the bundled catalog, and publication boundaries with external dependencies stubbed. These checks do not establish a whole-application production build or a live end-to-end write across both projects.
