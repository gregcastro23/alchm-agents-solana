# Project MCP server: protocol upgrade research

Research date: October 16, 2026. Scope: current official MCP specifications and Python SDK documentation, applied to the project's Python stdio server and desktop client boundary. This memo records recommendations, not implemented changes or verification of a deployed server. Sources were checked live; only first-party protocol and SDK sources are used.

## Implementation update — October 17, 2026

Phase 3 now uses the official SDK `mcp==2.3.0` with typed contracts and a paired
desktop adapter. The tagged release supports Python 3.10+; the project chooses
Python 3.11+ for its build/runtime baseline. The earlier statement about the
repository's 3.11 minimum describes SDK `main`, not the pinned release's metadata.
See the [Phase 3 verification record](mcp-phase3-2026-10-17.md). Remaining
recommendations below describe later phases rather than capabilities already
implemented.

## Recommendation

Keep the desktop stdio transport and move protocol handling into the official Python SDK behind explicit, typed project services. Improve authentication, input/output contracts and execution lifecycle before adding more tools. Upgrade the Python sidecar and TypeScript/Rust desktop client together, with legacy compatibility tests. A hosted HTTP MCP endpoint is a separate product decision, not a prerequisite for these improvements.

The project's `backend/planetary_agents_mcp_server.py` currently defaults to protocol `2025-06-18`, implements its own `initialize`/`ping`/dispatch/stdin loop, and awaits each handler before reading the next message. Its tool results are JSON serialized inside text content. These are repository observations, not claims about production deployment. The protocol loop deserves a smaller maintenance surface; cancellation also requires the process to keep reading while a handler runs.

## Current protocol and SDK baseline

The official `/specification/latest` endpoint resolves to **2026-07-28**, superseding the handshake-era baseline. The current revision removes `initialize`, introduces `server/discover`, and moves protocol version and client capabilities into each request's `_meta`. Results require `resultType`; list/read caching has explicit metadata. It also deprecates roots, sampling and protocol logging. Updating a protocol version environment variable alone cannot implement these changes. [Official specification](https://modelcontextprotocol.io/specification/2026-07-28), [2026 changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog)

The official Python SDK now identifies **v2 as its stable line**; `MCPServer` replaces the old `FastMCP` import. Its first-party repository requires Python 3.11+. Its migration guide identifies dependency changes, including a higher Pydantic floor and transport-library changes. Pin a tested release and lock its transitive dependencies, then validate the PyInstaller sidecar rather than adding an unbounded `mcp` dependency. [SDK v2 overview](https://py.sdk.modelcontextprotocol.io/whats-new/), [SDK repository](https://github.com/modelcontextprotocol/python-sdk), [Migration guide](https://py.sdk.modelcontextprotocol.io/migration/)

The SDK supports discovery on stdio and modern clients can probe then fall back to a legacy handshake. Preserve the existing desktop client during migration; test actual supported legacy versions instead of inferring compatibility from a successful `initialize`. [SDK protocol versions](https://py.sdk.modelcontextprotocol.io/protocol-versions/)

Use object-shaped results while supporting older clients. Project recommendation: models for chat, catalog, debate, duel and menu results; bounded history/string/list sizes; explicit unavailable/fallback/source fields. | Discovery and caching       | `server/discover` is required in the 2026 revision and advertises versions, capabilities and guidance. Project recommendation: advertise only working features, return deterministic catalogs, distinguish public catalog freshness from private user context, and expose build/protocol identity for diagnostics. [Discovery](https://modelcontextprotocol.io/specification/2026-07-28/server/discover), [Caching](https://modelcontextprotocol.io/specification/2026-07-28/server/utilities/caching)                                                                                       |
| Resources                   | Resources are URI-addressed context. Project recommendation: canonical resources/templates for agent identity, verified sky snapshots, council editions and bounded conversation summaries. Return snapshot IDs and observation times so several agent calls can share one evidence set. Scope private resources by verified identity. [Resources](https://modelcontextprotocol.io/specification/2026-07-28/server/resources)                                                                                                                                                                |
| Prompts                     | MCP prompts are user-selected message templates, and prompt arguments are named strings. Project recommendation: curated consultation, council and culinary-debate workflows that reference canonical resources and typed tools; keep structured orchestration in application services. [SDK prompts](https://py.sdk.modelcontextprotocol.io/servers/prompts/)                                                                                                                                                                                                                               |
| Pagination and filtering    | Protocol catalog listing uses opaque cursors; clients must consume `nextCursor` until absent. Project recommendation: add bounded, documented filters to domain tools for agents, feeds and transcript history. Such tool arguments are application contracts, not a universal MCP filtering feature. [Pagination](https://modelcontextprotocol.io/specification/2026-07-28/server/utilities/pagination)                                                                                                                                                                                     |
| Explicit conversation state | The modern protocol treats the process as a transport, not a conversation. Project recommendation: return server-created conversation/council/job IDs, bind them to a verified principal, and require them on later calls. Do not derive continuity solely from an agent name or subprocess lifetime. [Protocol overview](https://modelcontextprotocol.io/specification/2026-07-28/basic)                                                                                                                                                                                                    |
| Progress and cancellation   | Clients opt into progress using `progressToken`; values increase and stop at completion. Stdio cancellation identifies the active JSON-RPC request. Project recommendation: keep a bounded task registry, continue reading while handlers execute, cancel downstream HTTP/model work where possible, and enforce per-operation deadlines. Show useful phases, never invented percentages. ## Authentication and transport boundaries

MCP's OAuth authorization specification applies to HTTP transports; it explicitly recommends environment-provided credentials for stdio. Keep the local subprocess model. Authenticate its downstream API calls using scoped credentials supplied by the trusted desktop runtime. Derive user identity and billing tier from verified credentials; model-provided `userId`, tier, or context must not become authority. If remote MCP is later needed, add a separate Streamable HTTP adapter with OAuth resource metadata and audience validation. [Authorization specification](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)

Stdio stdout is reserved for newline-delimited MCP messages; diagnostic logs belong on stderr. The client must correlate replies by request ID and gracefully close stdin before terminating a stuck sidecar. Project recommendation: exercise these requirements against the packaged binary, fragmented output and concurrent requests. [Stdio transport](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/stdio)

## Long-running work: experimental project rollout

Tasks were experimental in the 2025-11-25 core and now live in an official opt-in extension. The current extension returns durable task handles and uses `tasks/get`, `tasks/update` and `tasks/cancel`; older `tasks/result` examples are not the current interface. Both ends must advertise support. Treat adoption as **experimental for this project** until the TypeScript/Rust bridge and intended hosts support it. For now, ordinary typed `start/get/cancel` project tools can expose durable jobs without claiming Tasks interoperability. [2026 changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog), [Tasks extension](https://modelcontextprotocol.io/extensions/tasks/overview)

For menu generation and multi-agent debates, persist job ownership, budget, step results, expiration and cancellation state before acknowledging job creation. This is a project design recommendation: an asynchronous Python task alone does not provide durability across sidecar restarts.

## Observability and validation

SDK v2 supplies OpenTelemetry spans and trace propagation; exporting them requires configuring an exporter. Project recommendation: connect desktop request → MCP handler → frontend/FastAPI → provider spans with request, conversation, snapshot and workflow IDs. Track latency, errors, cancellations, fallback rates and budget consumption without recording credentials or full private prompts. Prefer stderr and OpenTelemetry over investing in the deprecated MCP Logging feature. [SDK OpenTelemetry](https://py.sdk.modelcontextprotocol.io/run/opentelemetry/), [2026 deprecations](https://modelcontextprotocol.io/specification/2026-07-28/changelog)

The official SDK offers in-memory client/server tests, while MCP Inspector covers interactive protocol inspection. Project recommendation: retain subprocess/packaged-sidecar checks in addition to in-memory tests. Cover legacy and modern discovery, malformed arguments, output validation, authorization boundaries, concurrent calls, cancellation during a slow request, partial-line framing, restart/EOF handling and cursor exhaustion. Mock providers so these checks neither spend model budget nor mutate production state. [SDK testing](https://py.sdk.modelcontextprotocol.io/get-started/testing/), [MCP Inspector](https://modelcontextprotocol.io/docs/2026-07-28/tools/inspector)

## Suggested order and acceptance gates

1. **Contract and trust:** typed schemas/results, verified identity at downstream boundaries, authoritative user/tier resolution, bounded inputs, redacted errors. Gate: invalid or forged identity/tier requests fail before billed or state-changing work.
2. **Protocol engine:** replace the manual dispatcher with the official SDK, keep stdio, lock dependencies, rebuild the sidecar. Gate: real desktop bridge passes existing behavior plus version negotiation, framing, concurrent call and shutdown checks.
3. **Interaction depth:** explicit conversation/workflow handles, shared sky snapshots, provenance and resource templates. Gate: a multi-agent workflow shares one evidence snapshot and reproducibly resumes by handle.
4. **Execution lifecycle:** bounded concurrency, request cancellation, progress, deadlines and correlated tracing. Gate: cancelling one slow operation frees its work while unrelated reads remain responsive.
5. **Optional durable Tasks/remote access:** add only with a demonstrated client need and compatibility matrix. Gate: persistence, ownership, restart, expiry and budget tests pass before extension advertisement or remote publication.
