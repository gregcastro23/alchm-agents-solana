### Shared retry policy (`lib/wten/delivery.ts`)

- Retried: timeouts, network errors, 5xx, 429 (honouring `Retry-After` up to 10s; longer ends the
  delivery), and any 409 indicating in-flight processing. This covers both a body carrying
  `status: "in_flight"` / `reason: "in_flight"` (WTEN Phase 40 `src/lib/hooks/inFlightConflict.ts`,
  pending merge) AND any 409 on routes where WTEN returns 409 only while processing (`feed`,
  `sync-event`, `agent-recipes` per `src/app/api/feed/route.ts:245-255`, `src/app/api/economy/sync-event/route.ts:128-132`,
  `src/app/api/internal/agent-recipes/route.ts:91-96`). WTEN's legacy 409 body on these routes is
  `{ ok|success: false, error: "conflict", message: "Event is currently being processed" }` with `Retry-After: 1`.
- Never retried: other 4xx. 409 without the in-flight marker = already applied on sync-credit and
  sync-debit; 409 on `internal/agent-sync` is rejected; 402 is final.
- Endpoints WTEN dedupes vs does not dedupe: All three routes (`feed`, `agent-recipes`, `sync-event`)
  are deduped on `Idempotency-Key` by WTEN's `webhook_events` inbox since `5c79ef14`. `feed` and
  `agent-recipes` now safely retry all transient failures (`receiverDedupes: true`). `sync-event`
  keeps the narrow retry policy (`receiverDedupes: false`, retrying only 429, 503, connect-phase errors)
  because WTEN's inbox re-claims and re-runs a failed event after 300s, and `QuestService.reportEvent`
  increments quests in a non-transactional loop. If an increment throws, re-running increments earlier quests again.
- Residual risk on `sync-event`: If WTEN's first attempt fails part-way through `reportEvent`, a retried
  delivery (triggered by WTEN's 409 in-flight response or Phase 40 marker) will re-run `reportEvent`
  and double-count quests that already incremented. We accept this risk because losing the event entirely
  is the worse and far more common failure mode, and WTEN's own Phase 40 in-flight marker would trigger
  retries regardless. The real fix is WTEN making `QuestService.reportEvent` atomic.
- Backoff: equal jitter in `[cap/2, cap]`, `cap = min(4s, 250ms·2^(n-1))`, 3 attempts, and never past
  an optional caller deadline. Attempts are logged as `[wten-delivery] {json}` without headers.
- Fail-fast: once a delivery exhausts its attempts without any response (timeouts, network errors),
  every delivery in the next 60s makes a single attempt; any response clears it. The agent tick
  delivers per agent in sequence, so an unreachable WTEN costs one timeout per call, not three.
- Every attempt is recorded in `wten_deliveries` (`lib/wten/delivery-log.ts`, 14-day retention) and
  shown on `/admin/wten`; the write is capped at 2s and never fails a delivery.

## 3. Every place the two secrets are used interchangeably

The intended split: `ALCHM_KITCHEN_SYNC_SECRET` in `X-Sync-Secret` for the economy and agent-sync
routes; `INTERNAL_API_SECRET` as `Bearer` for feed and service calls. These sites cross it:

1. `lib/security/internal-auth.ts:37-41` — `hasInternalApiSecret` expects `INTERNAL_API_SECRET || ALCHM_KITCHEN_SYNC_SECRET`, presented in **any** of Bearer / `X-Sync-Secret` / `X-Internal-Secret`. Used by `/api/solana/health`, ASOL's own `POST /api/feed` (`app/api/feed/route.ts:216`), `/api/cron/purge-guest-chats`. Consequence for WTEN: a 401 from `/api/solana/health` means "the apps don't share `INTERNAL_API_SECRET`" only when ASOL has `INTERNAL_API_SECRET` set.
2. `backend/main.py:1996-2004` (Python agent-sync) — reads the `X-Sync-Secret` header (the `ALCHM_KITCHEN_SYNC_SECRET` header everywhere else) but compares it to `INTERNAL_API_SECRET`. WTEN matches this: it sends `X-Sync-Secret: INTERNAL_API_SECRET` (`src/app/api/admin/agent-sync/route.ts:76`).
3. `app/api/internal/group-chat/route.ts:29-43` — same crossing: `X-Sync-Secret` compared to `INTERNAL_API_SECRET || PA_INTERNAL_API_SECRET`; WTEN sends `X-Sync-Secret: INTERNAL_API_SECRET` (`src/app/api/agents/group-chat/route.ts:117`).
4. `lib/wtenClient.ts:42` — `INTERNAL_API_SECRET || ALCHM_KITCHEN_SYNC_SECRET`, sent as Bearer for the weekly-menu calls.
5. `lib/agents/feed-pusher.ts:49` — `INTERNAL_API_SECRET || WHATTOEATNEXT_API_KEY`.
6. `backend/main.py:2072` (Python purge cron) — `PA_CRON_SECRET || CRON_SECRET || INTERNAL_API_SECRET || ALCHM_KITCHEN_SYNC_SECRET`.
7. `backend/main.py:2128` (synthetic MCP probe) — `PA_CRON_SECRET || INTERNAL_API_SECRET`.
8. `backend/main.py:2336` and `pa-rust-backend/src/config.rs:52` — `PA_INTERNAL_API_SECRET || INTERNAL_API_SECRET`.

## 7. Verified sync-status receiver (2026-09-30)

`GET /api/economy/sync-status?idempotencyKey=` exists on WTEN master, shipped 2026-09-23.
Verified source: `src/app/api/economy/sync-status/route.ts` at the WTEN commit above.

`fetchKitchenStatus` in `lib/pentacles/reconciler.ts` calls it for Pentacle→ESMS conversions
whose sync-credit outcome was uncertain. The receiver compares `X-Sync-Secret` with
`ALCHM_KITCHEN_SYNC_SECRET` using `safeEqual` (401 on mismatch), requires a nonblank key
(400 otherwise), and trims it. It probes `token_transactions` for the exact key, the
`key:%` prefix, `source_id = key`, or a description matching the prefix. If none match,
it probes `webhook_events` for a processed event with that key.

A successful read returns `200 {ok:true, idempotencyKey, applied:boolean}`, echoing the
trimmed key. A database failure returns 500 `database_error`; it never returns
`applied:false` on failure. The current route does not return `appliedAt` or
`transactionCount`, impose the originally requested 255-character limit, or explicitly
set `Cache-Control: no-store`; it is force-dynamic and ASOL requests no-store.

ASOL accepts only a 2xx JSON answer echoing its exact key with a boolean `applied`.
Everything else is unknown and leaves escrow untouched. The route’s presence closes the
missing-receiver gap; scheduling is separate. ASOL checks only escrows older than ten
minutes and does not resend their credits after the original request, but WTEN’s maximum
late-commit window remains unverified here.
